# Red Skill 调研与证据协议

本协议来自历史 CC「Skills 规范深度调研 v2」和已经投入使用的 Skill 契约，已删除 Claude Code、视频生产线和私有项目专属要求，保留适合公开 Red Skill 的通用部分。

## 1. 最小调研门

创建文件前，先回答六个问题：

1. 用户会在什么原话或场景下需要它？
2. 它产出的可检查结果是什么？
3. 已有 Skill、通用模型能力或简单提示词为什么不够？
4. 核心方法、分类、阈值和依赖分别有什么依据？
5. 哪些情况必须拒绝、降级或提示不确定？
6. 它与最相邻的两个 Skill 如何区分？

任一关键问题答不清，候选保持 `researching` 或 `hold`，不靠补文案进入开发。

## 2. 两条证据路线

### 路线 A：样本反推

适用于有合法、可分析的真实案例或用户自有数据时。

- 同时看成功样本与对照样本，避免只从赢家总结万能规律。
- 规律至少在多个独立样本中复现，并记录反例。
- 将事实、归纳规则和仍待验证的假设分开。
- 样本只用于研究；除非权利清楚且运行必需，不进入公开 Skill 包。

### 路线 B：公开调研

适用于没有足够真实语料的冷启动主题。

- 优先官方规范、原始论文、源代码和维护者说明。
- 使用行业案例与真实用户反馈补充可用性和失败模式。
- 搜索摘要只用于发现来源，不作为最终证据。
- 找不到可靠依据时明确写“未找到”，不要凑结论或虚构阈值。

两条路线最终都要得到同一种开发记录，不能因为路线 B 写得像确定事实就提高可信度。

## 3. 依据等级

| 等级 | 含义 | 可以支持什么 |
|---|---|---|
| E1 | 用户自有真实数据、可复现实验或直接运行结果 | 核心机制、阈值和高置信结论 |
| E2 | 官方规范、原始论文、源代码、维护者一手说明 | 能力边界、接口、通行做法和设计选择 |
| E3 | 多个可信案例或独立用户证据交叉一致 | 使用场景、常见失败和软性建议 |
| H | 从 E1-E3 推导但尚无直接证据的假设 | 仅能进入实验项，必须附验证方法 |

禁止把 LLM 输出、单个搜索摘要、单个爆款或作者自评直接当成 E1-E3。禁止手工调高置信状态；只有新证据或真实使用结果可以升级。

## 4. 内部设计记录

批量清单为每个候选保留以下字段；它们属于开发记录，不要求全部塞进公开 Skill 包：

```yaml
skill_id: stable-kebab-case-id
version: 1.0.0
parent_version: null
research_route: A | B | mixed
purpose: 一句话真实用途
triggers: [正向触发]
non_triggers: [反向触发]
inputs: [必要输入]
outputs: [可检查输出]
target_users: [目标用户]
dependencies: [公开且必要的依赖]
evidence:
  - id: E01
    level: E1 | E2 | E3 | H
    claim: 支持的具体规则
    source: 可回溯来源或实验路径
    license_or_rights: 权利说明
risks: [风险与降级]
differentiation: 与相邻 Skill 的分工
confidence_state: cold-start | evidence-backed | field-validated
```

`skill_id` 稳定不变。版本升级要能从 Git 历史追溯，并说明新证据、修复或行为变化；不要通过改名切断血缘。

## 5. 从研究到 Skill

把研究结论转为运行规范时遵守以下规则：

- 每条核心规则至少能追溯到一个证据 ID；H 级只能写成可关闭或可验证的实验行为。
- `description` 写明“做什么 + 何时使用”，不要塞实现史和宣传语。
- 正向触发、反向触发和与相邻 Skill 的差异必须进入 `SKILL.md`。
- 主文件目标不超过 300 行；细节按需放入 `references/`，脚本只承载确定性逻辑。
- 命令必须能直接执行；说明性伪代码不能冒充执行步骤。
- prompt 中的强硬措辞不等于确定性约束。需要硬校验就提供脚本、schema 或测试，并如实声明宿主限制。
- 结构化文件只有在后续步骤确实读取时才生成，避免“零消费者指标”。

旧项目的“公式 + manifest + USAGE 三件套”在 Red Skill 中改为逻辑契约：`SKILL.md` 承担入口和使用边界，必要的详细规范放 `references/`，机器校验放 `scripts/`。不强制额外打包无运行价值的 `manifest.json` 或 `USAGE.md`。

## 6. 验证与反证

至少准备：

- 两个代表性正向请求；
- 一个容易误触发的相邻请求；
- 一个非法、缺失或高风险输入；
- 一条核心规则的反例；
- 依赖缺失、网络失败或权限不足时的行为。

计算或转换类 Skill 使用固定黄金样例和边界测试。判断、写作或解读类 Skill 要核对输出结构、证据边界、拒绝条件和一致性，不能只看“读起来不错”。

## 7. 公开包隔离

以下内容默认留在研究工作区，不进入 Skill 目录和公开 GitHub 仓库：

- `_research/`、`research/`、`corpus/` 中的原始材料；
- 抓取缓存、网页副本、转录全文和竞品完整副本；
- `output/`、日志、运行状态、备份和临时文件；
- 私人数据库、未脱敏样本、Cookie、密钥和内部基础设施信息；
- 没有再分发权的文章、课程、图片、代码或数据集。

确实属于运行时必要知识的研究结论，应重写为原创、最小、可归因的规范，并完成许可证与隐私检查后再放入 `references/`。
